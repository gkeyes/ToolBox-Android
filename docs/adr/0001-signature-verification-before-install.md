# ADR 0001：安装前完成完整性与签名验证

- 状态：Accepted
- 日期：2026-08-28

## 背景

`CODEX_PROMPT.md` 原阶段划分把完整性和 Ed25519 放在阶段 5，但阶段 2 已允许安装；技术方案的检查流水线要求先验证 `integrity.json` 和签名，`AGENTS.md` 又规定无效签名必须阻断。若按旧顺序执行，会出现“带签名但尚未验证”的包可以进入安装事务的窗口。

## 决策

阶段 2 的 `:tool-package` 检查器必须：

1. 按原始 `integrity.json` 字节验证 Ed25519，不重排或规范化被签名 JSON；
2. 验证文件集合及 SHA-256 覆盖，额外、缺失、篡改或格式错误均产生阻断结果；
3. 将 `INVALID` 作为不可覆盖的安装阻断状态；
4. 允许合法未知发布者和无签名包进入后续严格审核，但不得把它们标记为可信。

阶段 5 只增加发布者信任库、指纹展示、无签名工具限制和相关审核体验，不延后最低安全校验。

## 备选方案

- 保持原阶段顺序并允许安装：违反无效签名阻断不变量，拒绝。
- 阶段 2 暂时拒绝所有带 `signature.json` 的包：安全但破坏有效签名包的正常导入，且会产生临时兼容行为，拒绝。

## 影响

- 不改变模块边界：校验仍属于 `:tool-package`，发布者持久化仍属于 `:core-data`。
- Task 8 增加最低完整性/签名校验，Task 25 聚焦信任策略与 UX。
- Task 9 的安装入口只接受非 `INVALID` 的不可变检查会话。

## 验证

遵守 `TESTING.md` 的最小测试准入规则：使用一组参数化包矩阵覆盖有效、缺失、额外、篡改、原始字节变化与无效签名；预期所有无效行在进入安装协调器前被阻断且不留下会话残留。
